# FE-1.1 — Self-registration: design

**Story:** [`brain/stories/frontend/FE-1.1.md`](../../../brain/stories/frontend/FE-1.1.md) · **PRD:** US-1.1 in [`brain/docs/PRD.md`](../../../brain/docs/PRD.md) · **Related:** [BE-1.1](../../../brain/stories/backend/BE-1.1.md) (done, on `main`)

This is the first frontend vertical slice built on the `apps/web` scaffold. It establishes the BFF Route Handler pattern (`ARCHITECTURE.md` §6.1) that every later mutation-driven frontend story (login, verification, enrolment) will follow, and resolves the CAPTCHA provider choice deferred by BE-1.1 (§"Out of scope").

## Scope

- `/register` page: form (full name, email, phone, password, confirm password, T&C checkbox, Turnstile challenge).
- `/register/check-email` page: post-submit confirmation, showing the submitted address and a resend control.
- `app/api/register` Route Handler: the BFF proxy — verifies the CAPTCHA token, then forwards to BE-1.1's `POST /identity/register`.

No session/cookie logic is involved. Registration does not authenticate the user (`ApplicationUser.Status = PENDING_VERIFICATION`); session issuance is scoped to login (US-1.3), not this story.

## Architecture decision: CAPTCHA provider

Resolves the choice BE-1.1 deliberately deferred.

**Decision: Cloudflare Turnstile**, verified server-side inside the Next.js Route Handler — not inside the ASP.NET API.

- Turnstile over reCAPTCHA/hCaptcha: free, privacy-respecting (no third-party ad-tracking data flow), typically non-interactive, and its accessibility mode satisfies AC-1.1.10 (screen-reader and keyboard operable) without extra integration work.
- Verified in the BFF, not the API: keeps `MIM.Portal.Api`/`Application` provider-agnostic — no CAPTCHA-vendor dependency enters the backend, no `RegisterCommand` field change, no re-touching of BE-1.1's already-merged, tested slice. This matches §6's framing of the BFF as the layer that owns browser-facing concerns (session, CSRF) — CAPTCHA is another browser-facing concern of the same kind.
- Keys are read from env vars (`TURNSTILE_SITE_KEY` public, `TURNSTILE_SECRET_KEY` server-only). Local/dev defaults to Cloudflare's published test keys (always-pass) so the flow runs out of the box without a Cloudflare account; real keys are supplied via deployment env config, out of scope for this story.

## Flow

```
Browser (RegisterForm, Client Component)
  │  fills form, solves Turnstile challenge (widget calls Cloudflare directly for the client-side token)
  ▼
POST /api/register  (Next.js Route Handler — app/api/register/route.ts)
  │  1. verify Turnstile token → https://challenges.cloudflare.com/turnstile/v0/siteverify
  │     - fail → 400 { error: "captcha_failed" }, no call to the API
  │  2. forward { fullName, email, phone, password, passwordConfirmation } to
  │     POST {API_BASE_URL}/identity/register   (server-to-server, no browser exposure)
  │  3. translate API response:
  │     - 200 → 200 { email }
  │     - 400 (validation / AC-1.1.2 generic failure) → 400 { error: "registration_failed", message: <passthrough generic message> }
  │     - 429 → 429 { error: "rate_limited", message: <passthrough> }
  ▼
Browser: on 200 → router.push(`/register/check-email?email=${email}`)
         on 4xx  → inline error shown in RegisterForm (banner or field-level per AC-1.1.4)
```

```

└── lib/
```

**`register-form.tsx`**
- `react-hook-form` + `zod` resolver (the shadcn-documented form pattern). Client-side schema: email format, password length ≥ 10 (AC-1.1.3), password/confirmation match (AC-1.1.4, error attaches to the confirmation field only — neither field is cleared, since RHF preserves field values on validation failure by default), T&C checkbox must be `true` (AC-1.1.5).
- T&C/Privacy links: plain `<a target="_blank" rel="noopener noreferrer">`, pointing at placeholder routes (`/terms`, `/privacy`) — those pages themselves are out of scope for this story; a TODO marks them.
- Turnstile widget via `@marsidev/react-turnstile` (`<Turnstile siteKey={...} onSuccess={setToken} />`); submit button stays disabled until a token is present, satisfying "challenge blocks submission" without a separate error state.
- On submit: `fetch('/api/register', { method: 'POST', body: ... })`. Success → redirect (see Flow). Failure → error surfaced per the API's `error` discriminant: `registration_failed`/`rate_limited` render as a form-level `Alert`; a client-side validation failure (shouldn't reach the network, but defensively handled) renders field-level.

**`check-email/page.tsx`**
- Server Component. Reads `email` from `searchParams`; if absent, redirects to `/register` (defensive — this route isn't meant to be linked to directly).
- Static copy: "Check your email", the address, "We sent a verification link to this address."
- Resend button: rendered but `disabled`, with a tooltip/help text ("Resend will be available soon") — AC-1.2.5/1.2.6's resend semantics belong to BE-1.2/FE-1.2, which don't exist yet. This keeps AC-1.1.7 ("shows... a resend control") visually satisfied without inventing a fake endpoint.

**`lib/turnstile.ts`**
```ts
export async function verifyTurnstileToken(token: string, remoteIp?: string): Promise<boolean>
```
Posts to Cloudflare's `siteverify`, returns `body.success`. Called only from `app/api/register/route.ts` (never from a Client Component — the secret key never reaches the browser).

## Error handling

| Condition | Source | User-facing result |
|---|---|---|
| Field validation (length/match/format/unticked checkbox) | client-side zod, before submit | Field-level error, inputs retained (AC-1.1.4) |
| Turnstile verification fails | Route Handler | Form-level banner: "Verification failed — please retry." Turnstile widget auto-resets. |
| Duplicate email / any registration failure | ASP.NET API (passthrough) | Form-level banner with the exact AC-1.1.2 generic message — never field-attributed, so it can't disclose which field caused it |
| Rate limit (429) | ASP.NET API (passthrough) | Form-level banner with the API's human-readable message |
| Network/unexpected error | fetch failure | Generic fallback banner ("Something went wrong, please try again") |

No password value is ever logged — the Route Handler forwards the request body without logging it, matching AC-1.1.8's spirit at the BFF boundary (hashing/logging discipline itself is BE-1.1's concern, already covered).

## Testing

- **Vitest + RTL** (`components/register-form.test.tsx`): password-mismatch shows field error without clearing either field; short password rejected; unticked checkbox blocks submit; Turnstile-gated submit button stays disabled until a token callback fires (mock the widget).
- **Vitest** (`app/api/register/route.test.ts`): mocks `verifyTurnstileToken` and the upstream fetch to BE-1.1; asserts correct status/error-shape translation for each of the four response cases in the Flow table.
- **Playwright smoke test**: happy path only — fill form (using Turnstile's documented always-pass test site key), submit, assert redirect to `/register/check-email?email=...` and that the page shows the address.

- Session/login — registration does not authenticate; that's US-1.3.

# BE-1.1 — Self-registration: design

**Story:** [`brain/stories/backend/BE-1.1.md`](../../../brain/stories/backend/BE-1.1.md) · **PRD:** US-1.1 in [`brain/docs/PRD.md`](../../../brain/docs/PRD.md) · **Related:** [FE-1.1](../../../brain/stories/frontend/FE-1.1.md)

This is the first vertical slice built on top of [BE-0.1](../../../brain/stories/backend/BE-0.1.md)'s scaffold. It resolves three open architecture decisions (`ARCHITECTURE.md` §11: AD-2, AD-3, AD-4) that every later backend slice will follow.

## Architecture decisions resolved here

| # | Decision | Resolution |
|---|---|---|
| AD-2 | Mediator | Hand-rolled `ICommandHandler<TCommand,TResult>` in `Application.Common`. No MediatR dependency — avoids its commercial-licensing terms and the story only needs simple request→handler dispatch. Api endpoints resolve the concrete handler via DI and call `Handle` directly; no dispatcher/`ISender` indirection. |
| AD-3 | Email/background jobs | `Channel<EmailMessage>` + a hosted `BackgroundService` consuming it, retrying failed sends ≥3× with backoff (per §8's AC-5.2.4). `IEmailSender.Enqueue(...)` is non-blocking for the request. The concrete sender implementation logs the message (including the verification link) via `ILogger` — no real SMTP/provider wired up yet; swap the implementation later without touching callers. |
| AD-4 | Identity | ASP.NET Identity, **not** a custom slim layer (overrides the doc's prior "leaning custom" — see placement note below). |

`ARCHITECTURE.md` §11 will be updated to reflect all three as resolved, and §4.1/§6.3 updated for the Identity-placement note below.

## Identity placement vs. Domain purity

`IdentityUser<Guid>` lives in `Microsoft.AspNetCore.Identity`, so it cannot be the `Domain.User` entity without breaking §4.1's "Domain has zero framework references" rule — a rule that exists specifically so Phase 8's mobile client can reuse `Application` without web-specific leakage.

Resolution: **Identity's user lives in `Infrastructure` only.**

- `Infrastructure/Identity/ApplicationUser.cs` — `ApplicationUser : IdentityUser<Guid>`, adding `FullName`, `Phone`, `Role` (enum), `Status` (enum: `PENDING_VERIFICATION` | `ACTIVE` | `SUSPENDED`).
- `Infrastructure/Persistence/PortalDbContext.cs` becomes `PortalDbContext : IdentityDbContext<ApplicationUser, IdentityRole<Guid>, Guid>`. Identity's tables (`AspNetUsers`, `AspNetRoles`, etc.) are configured to `snake_case` naming per §7.1, same as every other table.
- `Domain` stays framework-free: it gets `StudentProfile` and `Token` (see below), which reference a user only via a plain `Guid UserId` — no dependency on `ApplicationUser` or Identity types.
- `Application` never touches `UserManager<ApplicationUser>` or any Identity type directly. It depends on a small interface it owns:

  ```csharp
  // Application/Common/IIdentityService.cs
  public interface IIdentityService
  {
      Task<IdentityResult<Guid>> CreateUserAsync(string email, string password, string fullName, string phone, CancellationToken ct);
      // CreateUserAsync returns a generic failure (no "email taken" detail) on any creation failure —
      // the handler is responsible for AC-1.1.2's non-disclosure, not this interface.
  }
  ```

  `Infrastructure` implements it by wrapping `UserManager<ApplicationUser>`.

This keeps the Clean Architecture dependency direction intact (`Domain` ← `Application` ← `Infrastructure`) while still getting Identity's lockout/token-provider plumbing for later stories (login throttling in US-1.3, etc.).

## Domain entities

```
Domain/
├── StudentProfile.cs   -- Id, UserId (Guid), StudentReference, DateOfBirth, NicOrPassport,
│                          Address, HighestQualification, CreatedAt, UpdatedAt
└── Token.cs            -- Id, UserId (Guid), Type (EMAIL_VERIFICATION | PASSWORD_RESET),
                           TokenHash, ExpiresAt, ConsumedAt, CreatedAt
```

Both are plain classes with domain methods where relevant (e.g. `Token.IsValid(DateTime now) => ConsumedAt is null && ExpiresAt > now`) — no EF Core or ASP.NET references, matching every other Domain entity.

`student_reference` format: `MIM-{year}-{00001}` (5-digit, zero-padded). Generated via a Postgres sequence (`student_reference_seq`, global — not reset per year) read at `StudentProfile` creation time, formatted as `MIM-{DateTime.UtcNow.Year}-{sequence:D5}`. A DB sequence avoids races under concurrent registrations without app-level locking; a unique index on `student_reference` is the backstop.

## Application slice — `Application/Identity/Register/`

```
Register/
├── RegisterCommand.cs      -- FullName, Email, Phone, Password, PasswordConfirmation
├── RegisterValidator.cs    -- FluentValidation: email format, password >= 10 chars, password == confirmation
├── RegisterHandler.cs      -- ICommandHandler<RegisterCommand, RegisterResult>
└── RegisterResponse.cs     -- Email (echoed back for the "check your email" page)
```

**Validator** checks format/length/match only — it does **not** check email uniqueness. Uniqueness is checked in the handler so that AC-1.1.2's non-disclosing generic error applies uniformly regardless of cause; a distinct "email already taken" validation error would itself leak account existence.

**Handler flow:**
1. Call `IIdentityService.CreateUserAsync(...)` with `role = STUDENT`, `status = PENDING_VERIFICATION`.
2. On any creation failure (including email conflict) → return `Result<RegisterResponse>.Failure("registration-failed", <the exact AC-1.1.2 generic message>)`. No field-level distinction is exposed to the caller.
3. On success → create `StudentProfile` (with generated `student_reference`), issue an `EMAIL_VERIFICATION` `Token` (24h expiry; only `TokenHash` persisted, per AC-1.2.1 — the raw token is embedded in the verification link and never stored), enqueue the verification email via `IEmailSender.Enqueue(...)`.
4. Return `Result<RegisterResponse>.Success(new RegisterResponse(Email))`.

Password hashing: Argon2id via the `Konscious.Security.Cryptography.Argon2` NuGet package (MIT-licensed), wired in as a custom `IPasswordHasher<ApplicationUser>` that replaces Identity's default PBKDF2 hasher — per §6.3's explicit requirement for a memory-hard algorithm. `UserManager` calls this transparently; no plaintext password ever reaches a log (AC-1.1.8).

## Cross-cutting

- **Rate limiting**: `Microsoft.AspNetCore.RateLimiting` (built into ASP.NET Core, no extra package). A fixed-window limiter keyed by client IP, 5 requests/hour, applied to the register endpoint. Exceeding it returns `429` with a human-readable problem-details body (AC-1.1.9).
- **Email queue**: `Infrastructure/Email/EmailQueueBackgroundService.cs` (`BackgroundService`) reads from an injected `Channel<EmailMessage>`. `Infrastructure/Email/LoggingEmailSender.cs` implements `IEmailSender` by writing to the channel; the background service's send step (for now) logs via `ILogger` rather than calling a real provider. Retries ≥3× with backoff on send failure, per the non-functional email-retry requirement.
- **CAPTCHA (AC-1.1.10)**: explicitly **out of scope** for this slice. No `IChallengeVerifier` or `CaptchaToken` field is added yet — it lands with FE-1.1 once a CAPTCHA provider is chosen (the frontend widget and the backend verify-call are two halves of the same decision, and picking a vendor mid-backend-only slice would be premature). Rate limiting still applies in the meantime.

## API endpoint

`MIM.Portal.Api/Endpoints/Identity/RegisterEndpoint.cs`:

```
POST /identity/register
  body: RegisterCommand (as JSON)
  200: RegisterResponse
  400: ProblemDetails (validation failure or registration failure — AC-1.1.2's generic message)
  429: ProblemDetails (rate limit exceeded)
```

Registered via `MapGroup("/identity")` per §4.1's Api-layer convention (endpoint groups, DTOs, problem-details mapping).

## Testing

- **New test project**: `MIM.Portal.Application.Tests` — unit tests for `RegisterValidator` (format/length/match cases) and `RegisterHandler` (mocked `IIdentityService` and `IEmailSender`, covering: success path, duplicate-email path returns the exact generic message, token/StudentProfile creation).
- **Integration test**: a `WebApplicationFactory`-based test (new `MIM.Portal.Api.Tests` project) hitting `POST /identity/register` against a real (test) Postgres database, asserting: `ApplicationUser` row created with correct role/status, `StudentProfile` row with a well-formed `student_reference`, a hashed `Token` row, and an email enqueued (verified via a test double for `IEmailSender` or by inspecting the channel).
- Rate-limit behavior (429 on the 6th request/hour) covered by an integration test using the same `WebApplicationFactory`.

## Out of scope for BE-1.1 (tracked elsewhere)

- CAPTCHA/bot-abuse verification (AC-1.1.10) — deferred to FE-1.1.
- Consuming the verification token / activating the account — that's [BE-1.2](../../../brain/stories/backend/BE-1.2.md).
- Sending via a real email provider — the `IEmailSender` implementation is swappable later without touching `Register`'s handler or any other caller.
